# One-question-at-a-time answering mode for the public quiz (v1)

Adds a 一問一答 (one-question-at-a-time) answering mode alongside the existing 一括表示 (all-at-once) mode in the public React quiz app. When a quiz is selected, `loadQuiz` now routes to a new `chooseMode` step instead of straight to `quiz`; the user picks a mode and both paths converge on the same `selected` state, the same single `submitAnswers` call, the same `QuizResult` screen, and the same one-time `history.append`. The change is entirely client-side presentation: all logic lives in `frontend/src/pages/HomePage.tsx`, with supporting CSS in `styles.css` and a README note. No new dependencies, no backend, no `api.ts` contract change.

Watch for: nothing blocking. The one-by-one progress bar counts answered questions rather than position, which is an intentional deviation from the all-at-once bar's semantics but reads slightly differently to a user (possible). A user can jump to the last question and submit without visiting earlier ones, mapping them to -1 — consistent with all-at-once and the -1 contract, not a regression (confirmed).

**Verdict**: APPROVED

## High-level view

The mode split is done as a state-machine extension, not a fork of the submit path. `View` gains `chooseMode`; a new `AnswerMode` state (default `'all'`) decides which answering component renders under the single `quiz` view. Both `QuizTaking` and the new `QuizTakingOneByOne` receive identical props and call the same `handleSubmit`, so scoring, the result screen, and history recording are shared by construction rather than duplicated. The existing all-at-once component is untouched functionally.

The public-payload contract is respected: `QuizDetail.questions` is `PublicQuestion[]` with no `answerIndex`, and the new component only reads `q.n`, `q.text`, and `q.options`. There is no local grading anywhere in the answering flow; correctness is revealed only on `QuizResult` from `SubmitResult`. Unanswered questions remain absent from `selected` and map to -1 at submit.

Dependencies stay exactly `react` + `react-dom` — the only new import is the `useRef` React hook. No lockfile, no router, no backend/`api.ts`/`amplify.yml`/admin/auth changes. The new component reuses existing CSS primitives and adds only container/chooser classes built from existing design tokens, and the accessibility touch (focus moves to the new question's legend on navigation, guarded against initial mount) is implemented.

The main behavioral nuance to be aware of is that the one-by-one progress bar measures answered count, diverging subtly from a positional reading a user might expect from a one-at-a-time flow.

<summary>Details</summary>

### Mode selection as a state-machine step, not a submit fork

`loadQuiz` keeps its role as the single fetch entry point — it still calls `getQuiz` and resets `selected`/`result`; only its post-fetch routing changed from `setView('quiz')` to `setView('chooseMode')`. Under the `quiz` view, the render branches on `mode` to pick `QuizTakingOneByOne` vs `QuizTaking`, passing identical props to both. Because the two modes are two views over one state, there is no second submit/scoring/history path to keep in sync — `handleSubmit` is unchanged and shared, which is what makes the "submit once, record history once" property hold for the new mode for free.

### No mid-quiz grading; public-payload contract intact

`QuizTakingOneByOne` consumes only `q.n`, `q.text`, and `q.options` from each question. `answerIndex` does not exist on `PublicQuestion` and is referenced only in `QuizResult` (line 509) against `SubmitResult.results`, i.e. after server scoring. The 次へ button only calls `setCurrent` — advancing and answering are separate, so there is no path where correctness leaks before the result screen (confirmed).

### Unanswered = -1 preserved across both modes

`selectOption` only ever writes a real option index into `selected`; no code path stores -1. Navigating past a question without choosing leaves its `q.n` key absent, and `handleSubmit` maps `q.n in selected ? selected[q.n] : -1` over all questions regardless of mode, so a partially-answered one-by-one run submits the same -1 sentinels an all-at-once run would (confirmed). One consequence: on the last question the submit button is always enabled, so a user can submit having visited only some questions and the unvisited ones score as -1. This is identical to all-at-once (where the single 回答する is always enabled too), so it is not a regression — flag it only if product wants an explicit unanswered-count confirmation.

### Progress bar counts answers, not position

Both components compute `percent` as `answered / total`, where `answered = questions.filter(q => q.n in selected).length`. In one-by-one the bar sits above a "Q 3 / 5（回答済み 1 / 5）" label, so the fill reflects answers given, not how far you've stepped — someone stepping through with 次へ without answering sees the bar stay near empty while the "Q X / Y" climbs. The label disambiguates it, but this is a genuine semantic difference from what a one-at-a-time UI often shows (position). Worth a product confirmation; not a correctness issue (possible).
