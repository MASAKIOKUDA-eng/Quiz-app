# Admin single-quiz read/edit/delete routes + CORS locked to the Amplify origin

Adds three JWT-authorized routes on the existing quiz Lambda — an admin `GET` that returns each question *with* its `answerIndex` (for the editor's correct-answer pre-fill), a full-replace `PUT`, and a `DELETE` — and tightens CORS from `allowOrigins: ['*']` to a single configurable origin that defaults to the Amplify Hosting domain. The edit path is deliberately full-replace: it 404s if the quiz doesn't exist, then deletes all existing items and rewrites `META` + `Q#n` so `questionCount` and the question set always reflect the new payload. The origin is threaded end-to-end: the same `allowedOrigin` CDK context value feeds both the API Gateway preflight `allowOrigins` and the Lambda's `ALLOWED_ORIGIN` env var, which sets the `access-control-allow-origin` response header. Body validation for the edit is shared with the create route through a new internal `validateTitleAndQuestions` helper, so per-question rules can't drift.

**Watch for:** the full-replace edit is a non-atomic delete-then-write — a failure between the two steps leaves the quiz partially deleted with no rollback (confirmed). The admin routes gate on *authentication* only; any valid User Pool JWT can edit/delete every quiz, with no admin group/role check (confirmed — likely acceptable given the pool has self-signup disabled and is operator-provisioned, but worth an explicit decision).

**Verdict**: APPROVED

## High-level view

The three routes reuse the existing Lambda, the existing `getQuizItems`/`writeQuizItems` primitives, and the existing single `adminJwtAuthorizer`, so the change adds behavior without reshaping the topology. `PUT` and `DELETE` both 404 before mutating.

The delete primitive is a query-then-batch-delete because DynamoDB has no delete-by-prefix; it mirrors the write path's `<=25`-per-batch chunking and bounded `UnprocessedItems` retry and reuses the exact same key shapes, so a partial-key mismatch can't orphan items. The structural risk is that edit chains delete then write with no transaction, so a mid-operation failure is observable.

The admin `GET` intentionally includes `answerIndex` while the public `GET` still routes through `toPublicQuestions` and strips it — the sensitive field only leaks on the JWT-gated route. CORS is now a single origin on both the preflight and the actual response header, overridable per deploy via `-c allowedOrigin=`.

Tests were extended in lockstep: the handler suite imports the real `validateAndNormalizeQuizUpdate` and asserts path-id-wins plus every rejection branch; the stack suite asserts seven routes, JWT binding on all four admin routes, no wildcard origin, PUT/DELETE in allowMethods, and the Lambda env var matching the CORS origin. Not covered is the route-handler wiring itself — the delete-then-write sequence, the 404 guards, and the answerIndex-inclusive projection are pure-function- and template-tested but never exercised end-to-end.

<summary>Details</summary>

### Full-replace edit: 404 gating and non-atomic mutation

`PUT` validates the body, then re-queries with `getQuizItems` and 404s if `meta` is absent, so edit can never accidentally create a new quiz — the quizId is taken from the path and a body `quizId` is ignored.

The mutation is `deleteQuizItems(quizId)` followed by `writeQuizItems(validated.quiz)`, two independent BatchWrite sequences with no transaction spanning them and no rollback. If the delete succeeds and the write then fails (throttling past the 5-attempt retry, a Lambda timeout, an SDK error), the quiz is left with `META` and questions removed and nothing written back, and a public read of it 404s until the operator retries. For a low-traffic admin editor on an on-demand table this is unlikely and recoverable, but it is a real fail-partial window that the create route (single write, guarded by a 409 collision check) does not have. `TransactWriteItems` would make it atomic; if that's judged overkill for the demo, the non-atomicity is worth one README line so a future maintainer knows it's a considered choice.

### Delete-by-prefix via query-then-batch-delete

DynamoDB's document client has no delete-by-partition-key, so `deleteQuizItems` queries the item keys (`getQuizItems`, keyed on `pk = QUIZ#<quizId>`) and issues `DeleteRequest`s. It reconstructs keys from the stored `pk`/`sk` rather than re-deriving them, so the delete keys are guaranteed identical to what was written — no risk of an sk-format skew orphaning `Q#n` rows. The empty-key early return makes deleting a just-emptied quiz a no-op rather than an error, consistent with the 404 guard in front of it on both `PUT` and `DELETE`.

### answerIndex exposure is scoped to the authenticated read

The admin `GET /api/admin/quizzes/{quizId}` maps questions to include `answerIndex` explicitly, bypassing `toPublicQuestions`. The public `GET /api/quizzes/{quizId}` is untouched and still runs `toPublicQuestions`, which strips `answerIndex`. The leak-prone field is only ever returned on the JWT-gated route, and the public projection helper remains the single chokepoint for anonymous reads. Worth confirming the frontend admin client sends the `Authorization` header on this new `GET` (separate PR), since without it the route 401s at the authorizer rather than falling back to the public shape.

### CORS coherence end-to-end

The change closes the previous `allowOrigins: ['*']` gap by sourcing one `allowedOrigin` value (CDK context, defaulting to the Amplify domain) into both the preflight `allowOrigins` and the Lambda `ALLOWED_ORIGIN` env var that drives the `access-control-allow-origin` response header, so preflight and actual response advertise the same single origin. `PUT` and `DELETE` were added to `allowMethods` alongside GET/POST/OPTIONS. The env-var fallback to `'*'` only applies when `ALLOWED_ORIGIN` is unset, and the stack always sets it, so the wildcard can't reappear in a normal deploy.

### All admin routes bound to the JWT authorizer; no authorization tier

All three new routes are added with `authorizer: adminJwtAuthorizer` — the same instance protecting `POST /api/admin/quizzes` — and the stack test asserts JWT on all four admin route keys and none on the public routes. The open question is authorization, not authentication: a valid JWT from any User Pool member can edit or delete any quiz, because there's no group/role/claim check in the handler or the authorizer. Given the pool disables self-signup and admins are operator-provisioned, the blast radius is small, but "any authenticated user is a full admin" should be an explicit decision. If a non-admin user tier is ever added to this pool, these routes would silently become reachable by them.

### Test coverage

The handler suite adds a block for the real exported `validateAndNormalizeQuizUpdate`: it asserts the path argument wins over a body `quizId`, that title is trimmed and questions normalized, and it exercises every rejection branch (non-object body, empty title, empty/missing questions, `<2` options, blank option strings, out-of-range and non-integer `answerIndex`). The stack suite is tightened to seven routes, JWT on all admin routes, public routes open, `AllowOrigins` asserted as the literal domain and separately asserted *not* to contain `'*'`, PUT/DELETE present in allowMethods, and the Lambda's `ALLOWED_ORIGIN` env matching the CORS origin — each would fail if the corresponding change were reverted.

**Not tested:** the route handlers themselves. Nothing drives `handler()` for `PUT`/`DELETE`/admin-`GET`, so the 404-before-mutate guards, the delete-then-write ordering, the empty-key no-op, and the answerIndex-inclusive-vs-stripped divergence between admin and public reads are verified only by reading the code. A handler-level test with a mocked `ddb.send` would close this and would catch, for example, an accidental swap to `toPublicQuestions` on the admin read. (Read-based verification only; the sandbox is INTEGRATIONS_ONLY, so jest/cdk synth were not run.)
