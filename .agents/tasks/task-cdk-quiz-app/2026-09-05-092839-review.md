# Cost-minimized serverless quiz app on AWS CDK (v1)

A greenfield AWS CDK v2 (TypeScript) stack that stands up a fully-serverless quiz app: a private S3 bucket fronted by CloudFront serves a dependency-free vanilla-JS SPA, an API Gateway v2 HTTP API routes to a single ARM64 Lambda, and a DynamoDB single-table on-demand store holds quizzes. The design directly targets the user's three requirements — AWS, CDK, minimal cost, always-on serverless — by choosing only services that scale to zero and carry no idle charge (DynamoDB PAY_PER_REQUEST, Lambda, HTTP API, CloudFront PriceClass_100, no VPC/NAT). The Lambda strips the correct-answer index before returning questions and scores submissions server-side. Sample Japanese quiz data is auto-seeded on the first empty `GET /quizzes`.

**Watch for:** the frontend cannot reach the API out of the box — `config.js` ships `window.API_BASE = ''`, so the SPA calls same-origin paths that CloudFront resolves against S3, not the HTTP API (confirmed); CORS `allowOrigins: ['*']` is wide open (confirmed, acceptable for a public demo but worth a conscious decision); and `S3BucketOrigin.withOriginAccessControl` requires aws-cdk-lib ≥2.156 while package.json pins `^2.150.0` (likely a non-issue on a fresh install, a hard break if a lockfile pins 2.150). Build/synth/test were never run — no network in the sandbox — so compilation and template synthesis are unverified.

**Verdict**: NEEDS_CHANGES

## High-level view

The cost-minimization requirement is met convincingly: every resource in the stack is pay-per-use with no standing charge, and the README ties each choice back to idle cost. The stack tests assert the cost-relevant properties (on-demand billing, arm64, HTTP API, PriceClass_100, public-access-blocked) so a regression on any of them would fail CI.

The wiring between the SPA and the API is the weak seam. The frontend and the HTTP API live on different origins, but the shipped `config.js` leaves `API_BASE` empty, which resolves API calls to the CloudFront/S3 origin rather than the API. Because CloudFront maps 403/404 to `index.html` with a 200, a stray API call returns HTML and the SPA's JSON parse fails rather than surfacing a clear error. The README documents the manual "edit config.js, redeploy" step, so this is a known gap, but the app is non-functional until that step is done and there is no build-time injection of the endpoint.

Security posture is appropriate for a public quiz: the correct-answer index is stripped from question payloads and scoring is server-side, the S3 bucket is fully private behind Origin Access Control, and SSL is enforced. The open CORS and absence of auth/rate-limiting are deliberate demo trade-offs called out in the docs. The one dependency-versioning caveat (OAC origin helper vs. the pinned floor) is worth pinning down before a real deploy.

### Cost-minimization: the requirement, and how it is met

DynamoDB runs PAY_PER_REQUEST so there is no provisioned-capacity floor; the Lambda is ARM64/Graviton at 256 MB with a 10s timeout and scales to zero; API Gateway is the v2 HTTP API rather than the pricier REST API; CloudFront is PriceClass_100; and there is deliberately no VPC or NAT gateway, which is the usual hidden always-on charge in "serverless" stacks. The net effect is that idle cost is essentially S3 storage plus minimal CloudFront — the intended "looks always-on, bills near zero" shape the user asked for.

### Frontend-to-API origin gap

This is the one place where the pieces don't connect on their own.

```
Browser ──► CloudFront ──► S3 (static SPA)      window.API_BASE = ''
   │                                             app.js: apiUrl('/quizzes')
   └── fetch('/quizzes') ─────────────────────►  = '' + '/quizzes'
                                                  → https://<cf-domain>/quizzes
                                                  → CloudFront → S3 (no such key)
                                                  → 404 mapped to index.html (200)
```

`app.js` computes `API_BASE = (window.API_BASE || '').replace(/\/$/, '')` and prepends it to paths like `/quizzes`. With the shipped empty `API_BASE`, requests go to the CloudFront origin, which only knows the S3 bucket — the HTTP API is a separate `execute-api` origin that CloudFront is not configured to forward to. So the SPA is non-functional immediately after `cdk deploy`; the operator must edit `config.js` with the `ApiEndpoint` output and redeploy. The README documents this, so it is a known limitation rather than a hidden bug, but two things make it sharper than necessary: there is no deploy-time injection of the endpoint (BucketDeployment supports source substitutions, or a CloudFront behavior on `/api/*` pointing at the API would make same-origin `API_BASE=''` actually correct), and the 403/404→`index.html` error mapping means a misrouted API call comes back as HTML with a 200 status. `fetchJson` only checks `res.ok`, so a 200-HTML response slips past the status guard and throws on `res.json()`, surfacing to the user as a generic failure rather than anything diagnostic.

### Answer-stripping and server-side scoring

`GET /quizzes/{quizId}` rebuilds each question as `{ n, text, options }`, dropping `answerIndex`, so the client never receives the correct answers, and scoring runs in the Lambda via the pure `scoreAnswers` helper comparing `answers[q.n]` to the stored `answerIndex`. Unanswered or out-of-range positions score as incorrect rather than throwing, and the frontend cooperates by sending `-1` for unanswered questions — the client cannot inspect or bypass the correct answers.

### CORS and auth posture

CORS is configured with `allowOrigins: ['*']`, so any site can call the API from a browser; tightening to the CloudFront domain would be the production move. There is no authentication, authorization, or rate limiting on the write path (`POST /submit`) — the endpoint is internet-reachable and unmetered. The exposure is bounded because submit neither writes nor reads user identity and persists nothing per-user, but the open surface is worth a conscious decision rather than a default.

### DynamoDB access shape and seeding

`listQuizzes` uses a `Scan` with a `FilterExpression` on `sk = META`; negligible at the two-item demo scale, but a full-table scan that grows linearly with quiz count — a GSI over the META items is the pattern once the data set is non-trivial. Seeding fires when the META scan is empty, writing sample items via BatchWrite in 25-item chunks. It is idempotent by key, so concurrent cold-start seeds converge on identical items. One real gap: BatchWrite's `UnprocessedItems` are not retried, so under throttling a partial seed could persist and leave the table in a half-populated state on the first request; harmless at 8 items on an empty on-demand table, but the pattern is incomplete for larger seed sets.

### Dependency-version caveat on the OAC origin

`origins.S3BucketOrigin.withOriginAccessControl` was introduced in aws-cdk-lib 2.156.0, but `package.json` pins `aws-cdk-lib: ^2.150.0`. A fresh `npm install` resolves to the latest 2.x and picks up the method, so a clean checkout is fine — but a committed lockfile pinning exactly 2.150.x (or an offline mirror) would make `cdk synth` fail to compile. Raising the floor to `^2.156.0` documents the real minimum. Only a real build in a networked environment would catch this, which hasn't run here.

### Test coverage

`handler.test.ts` imports the real exported `scoreAnswers` (no reimplementation, no mocking) and covers all-correct, partial, all-wrong, empty answers, mismatched length, out-of-range indices, extra answers, and the empty-quiz case — it would fail if the scoring contract regressed. `quiz-app-stack.test.ts` synthesizes the real stack and asserts the cost-relevant properties (single on-demand table, arm64 Node Lambda, HTTP protocol, exactly three routes matched by RouteKey, CloudFront PriceClass_100, S3 public-access-block all-true), avoiding brittle logical-ID matching.

Not tested: the handler's routing and error paths (400/404/500, the answer-stripping projection, the empty-table seeding branch) are entirely untested — only the pure scoring helper is exercised. Since answer-stripping is the security-critical behavior, a handler-level test asserting `answerIndex` never appears in the `GET /quizzes/{quizId}` payload would be worth adding. The frontend has no tests. None of the tests have actually run (no network for `npm install`/`jest`/`cdk synth`), so their passing status is asserted by construction, not observed.
