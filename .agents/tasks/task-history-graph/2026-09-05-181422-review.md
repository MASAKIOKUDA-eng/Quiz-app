# Client-side quiz history with hand-rolled SVG charts (v1)

Adds a per-browser quiz history feature to the public React app without any backend, login, or new dependencies (案A). A pure, typed `history.ts` module persists each scored attempt to `localStorage` under a versioned envelope; a new `HistoryView` renders two dependency-free inline-SVG charts (score-over-time line, per-quiz average-accuracy bar) plus a recent-attempts list and a `window.confirm`-guarded clear action. It hooks into HomePage's existing no-router view state machine, recording exactly one record inside the successful submit callback so StrictMode double-invocation can't double-count. No charting or date library was added; theming rides existing CSS variables.

Watch for: the line chart plots attempts on an evenly-spaced index axis, not a real time axis, so uneven gaps between attempts are invisible (confirmed); the recent-attempts `key` uses `takenAt`+index rather than a stable id, harmless today but worth noting (confirmed); no automated test covers the `history.ts` logic and none can be added in this repo (confirmed). No security-relevant surface is touched — history never leaves the browser and no auth, token, or network path changes.

**Verdict**: APPROVED

## High-level view

The data layer is a side-effect-free module: every `localStorage` call is wrapped in try/catch, `load()` validates shape, version, and each record's field types before returning, and `append()` caps at `MAX_RECORDS=200` by keeping the newest and returns the trimmed array even when the write throws. The design degrades cleanly to empty history in private mode or when storage is disabled.

Recording happens in exactly one place — the successful branch of HomePage's async submit callback, right after `setResult(res)` — the correct choice under `React.StrictMode`. The percent formula in `makeRecord` mirrors HomePage's existing `Math.round(score/total*100)` (0 when total is 0), so recorded and displayed percentages agree.

The charts are inline `<svg>` with a fixed `viewBox` scaled to card width via `width:100%`, themed entirely through `var(--primary)`, `var(--muted)`, `var(--card-border)`, `var(--text)` and friends (all confirmed to exist in both light and dark palettes), with `role="img"`, `aria-label`, `<title>`, and textual value/axis labels so nothing depends on color alone. The line chart's x-axis is attempt order, not elapsed time — a simplification worth knowing when reading trends.

The integration is purely additive: the `View` union gains `'history'`, `QuizList` and `QuizResult` get an `onViewHistory` prop wired to `setView('history')`, and the existing list/quiz/result flow, scoring, score-ring, aria-labels, and Japanese copy are untouched. Dependencies remain exactly `react` + `react-dom` with no lockfile added, and no backend, API, amplify.yml, or admin file is in the diff.

<summary>Issues (4)</summary>

1. **Index-based time axis** — the line chart spaces attempts evenly by index, so a burst of attempts and attempts weeks apart look identical; acceptable for v1 but document or revisit if trend-over-time accuracy matters.
2. **Bar chart crowding at scale** — bar width and x-labels are computed from quiz count with labels truncated to 8 chars; with many quizzes labels overlap and bars get thin. Fine for the current small quiz set; consider a scroll or cap if the catalog grows.
3. **Recent-list key** — `key={`${r.takenAt}-${i}`}` mixes a timestamp with the render index; stable enough in practice but two attempts sharing a millisecond timestamp rely on index. Low priority.
4. **No test coverage** — `history.ts` (validation, cap, percent, aggregation) has no unit tests and the repo has no frontend test runner (none may be added here). Correctness rests on review + the user's `npm run build` type-check.

<summary>Details</summary>

### localStorage envelope: validation and fail-soft writes

`load()` is the trust boundary for untrusted stored data: missing key, non-object JSON, `version !== CURRENT_VERSION`, and non-array `records` each short-circuit to `[]`, and surviving records pass through `isHistoryRecord` which checks every field's type, so corrupt or partially-written entries are dropped rather than propagated. `append()` trims with `slice(-MAX_RECORDS)` and returns the in-memory trimmed array regardless of whether the write succeeded, so a quota or disabled-storage failure never blocks the UI from showing the just-completed attempt.

One consequence of the version check: any future bump of `CURRENT_VERSION` silently discards all existing history (returns `[]` on mismatch) with no migration path. A reasonable v1 stance for throwaway client data, but if history is ever worth preserving across releases, this is where a migration would go.

### Recording once, and only on success

```tsx
const res = await submitAnswers(quiz.quizId, answers);
setResult(res);
append(makeRecord({ quizId: quiz.quizId, title: quiz.title, score: res.score, total: res.total }));
```

Records are written only on the resolved-promise branch, so a failed API call leaves no phantom entry, and placing the call outside render/effect keeps it out of StrictMode's dev double-invocation.

### Charts: index x-axis and scale limits

The line chart maps attempt *index* to x (`indexToX(i, count)`), not `takenAt`. Consecutive attempts are always equidistant regardless of whether they were seconds or weeks apart, so what it shows is order-of-attempt, not rate-over-time — the one place the visual can mislead. `chronological` correctly sorts by `takenAt` before feeding the chart, so the issue is the axis mapping, not the data.

The bar chart computes `slot = plotW / count` and `barWidth = slot * 0.62`, truncating titles to 8 chars for x-labels. It scales down gracefully for a handful of quizzes but degrades (thin bars, clipped/overlapping labels) as the quiz catalog grows; bounded today, worth a second look later.

### Aggregation title-tiebreak

`averageByQuiz` groups by stable `quizId` but adopts the most-recent record's title via `record.takenAt >= existing.latestAt`, so display titles track admin renames while grouping stays stable. On identical timestamps the later-iterated record wins the title.

### Test coverage

No tests accompany the change and the frontend has no runner, which the environment forbids adding. The `history.ts` surface (shape validation, `MAX_RECORDS` trimming, percent rounding, `averageByQuiz`/`chronological`) is exactly the pure logic that would benefit from unit tests; that verification is deferred entirely to reading and the type-check in `npm run build` on a networked host.
