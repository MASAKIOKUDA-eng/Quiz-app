# Force the WebSocket prod stage to depend on every route (autoDeploy/route race fix) — review v1

The realtime-battle WebSocket handshake was failing with `close code=1006` and no `$connect` log ever reaching the ws Lambda, because the API Gateway v2 `autoDeploy` stage could publish before its routes existed, serving a partial route set with `$connect` missing. The fix removes the built-in `connectRouteOptions`/`disconnectRouteOptions`/`defaultRouteOptions` from the `WebSocketApi`, creates all ten routes (`$connect`, `$disconnect`, `$default`, plus seven battle actions) explicitly via `addRoute`, captures each returned `WebSocketRoute`, and then adds an explicit CloudFormation `DependsOn` from the prod `WebSocketStage` to every route so the auto-deploying stage is ordered after all routes. A new test derives the WS route logical IDs from the synthesized template and asserts the prod stage's `DependsOn` contains all of them; the README gets a Japanese note on redeploying (and the one-time console "Deploy API" stopgap).

Watch for: the stage-to-route `DependsOn` orders resource *creation* correctly (confirmed), but whether it forces API Gateway's implicit auto-deployment to *re-publish* on every subsequent route change is a weaker guarantee than the comments claim — worth understanding before treating this as a permanent fix for all future route edits (possible). Otherwise the change is tightly scoped with no regressions to the HTTP API, Cognito, `grantManageConnections`, or the `WebSocketEndpoint` output (confirmed).

**Verdict**: APPROVED

## High-level view

The fix targets the well-known API Gateway v2 quirk where an `autoDeploy` WebSocket stage has no implicit CloudFormation ordering against its `Route` resources. Moving the three built-in routes out of the `WebSocketApi` constructor options and into explicit `addRoute` calls is what makes the fix possible: `addRoute` returns a `WebSocketRoute` construct that the stage can depend on, whereas the `*RouteOptions` routes are created internally and are awkward to reference. The built-in route behavior is unchanged — same integration, same `$connect`/`$disconnect`/`$default` route keys, and no authorizer was ever attached that would drift.

The ordering guarantee comes from a loop calling `wsStage.node.addDependency(route)` for each of the ten routes, synthesizing a `DependsOn` array on the `AWS::ApiGatewayV2::Stage`. This guarantees the stage is created/updated after all routes on the initial deploy — exactly the failure that produced the outage. Whether it also forces a re-publish on every future route-set change is less certain, because `autoDeploy` is a property flag on the stage, not a discrete `CfnDeployment` resource that CloudFormation re-triggers.

The test asserts the guarantee structurally: it pulls WS route logical IDs from the template by `RouteKey` (not hardcoded), finds the single stage whose `StageName` is `prod`, and checks its `DependsOn` contains each route ID. The `prod` filter correctly disambiguates from the HTTP API's `$default` stage, and the test would fail if the `addDependency` loop were reverted.

### Moving built-in routes to explicit addRoute

The three built-in route keys previously came from `connectRouteOptions`/`disconnectRouteOptions`/`defaultRouteOptions` on the `WebSocketApi` constructor, which produce internally-created routes that are hard to reference for an explicit dependency. Creating them through `addRoute('$connect', { integration: wsIntegration })` (and the same for `$disconnect`/`$default`) yields a `WebSocketRoute` handle for each, collected alongside the seven action routes into `wsRoutes`. In aws-cdk-lib 2.156 `apigwv2.WebSocketRoute` is exported and is the return type of `WebSocketApi.addRoute`, so the typing (`const wsRoutes: apigwv2.WebSocketRoute[]`) is correct.

The synthesized `AWS::ApiGatewayV2::Route` for `$connect` created via `addRoute` carries the same `RouteKey` and Lambda integration the constructor option would have produced. The one capability `connectRouteOptions` adds that `addRoute` does not auto-wire is an `authorizer` — but none was configured here, so there is no behavioral drift on the handshake.

### The DependsOn ordering and the autoDeploy caveat (confirmed + possible)

```
wsRoutes[$connect, $disconnect, $default, createRoom, ... endGame]
        │  (each a WebSocketRoute -> AWS::ApiGatewayV2::Route)
        ▼
wsStage (AWS::ApiGatewayV2::Stage, autoDeploy:true, StageName 'prod')
   DependsOn: [ every route logical ID ]
```

`wsStage.node.addDependency(route)` renders at synth time as a `DependsOn` on the stage's CloudFormation resource covering the route (and, transitively, the shared integration the routes reference). This fixes the observed outage: on the initial deploy the stage — and the auto-deployment API Gateway performs when the stage is created — is ordered after every route exists, so the published prod stage carries the full route set.

The caveat is the comment's stronger claim that "every `npx cdk deploy` publishes the FULL route set." `autoDeploy: true` is a property on the stage resource, not a discrete `AWS::ApiGatewayV2::Deployment` that CloudFormation re-creates on each change; API Gateway performs the auto-deploy in response to route/stage changes on its side, and a `DependsOn` only orders resource creation/update within a single changeset. For the failure actually hit (routes and stage created together, stage racing ahead), this is the right and sufficient fix. For a hypothetical future change that adds a route without otherwise mutating the stage, whether this dependency guarantees a re-publish relies on API Gateway's auto-deploy semantics, not on CloudFormation ordering — a "possible" concern worth verifying if the route set changes later; it does not block the current fix.

### Test disambiguates the prod stage from the HTTP $default stage (confirmed)

The new test finds the WS stage by filtering `AWS::ApiGatewayV2::Stage` resources on `StageName === 'prod'`. The HTTP API (`QuizHttpApi`) is created with default options and no explicit stage name, so its stage synthesizes as `$default` — the `prod` filter therefore selects exactly the WebSocket stage. Route logical IDs are derived from the template by matching `RouteKey` against the WS key list rather than being hardcoded, so the test stays valid if CDK changes logical-ID hashing. Reverting the `addDependency` loop would leave the stage without the route IDs in its `DependsOn`, failing the `toContain` assertions — so the test exercises the changed path.

The "all ten WS routes present" length check overlaps the pre-existing `defines the WebSocket routes` test, which already asserts each WS `RouteKey` exists; it is a harmless sanity guard but is not what makes this test meaningful.

### No collateral changes (confirmed)

The HTTP API and CORS config, Cognito, `grantManageConnections`, and the `WebSocketEndpoint` output (`value: wsStage.url`, still `wss://.../prod`) are untouched, and the stage name stays `prod` so `WS_URL`/`VITE_WS_URL` consumers see no change. `lambda/ws.ts`, the frontend, `package.json`, and lockfiles are unchanged as intended; the README addition is documentation only.
