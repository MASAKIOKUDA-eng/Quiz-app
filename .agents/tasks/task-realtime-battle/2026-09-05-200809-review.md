# Realtime multiplayer quiz battle over a WebSocket API (v1)

Adds a synchronous multiplayer "battle" mode on top of the existing single-player quiz app: a Cognito-authenticated host creates a room from one of the already-registered quizzes, shares a short room id, and unauthenticated participants join with just a display name. A new API Gateway v2 WebSocket API fronts a dedicated ARM64 Lambda (`lambda/ws.ts`) that runs a server-authoritative state machine (lobby → in_question → between → finished), scores answers server-side against the stored `answerIndex`, and fan-out-broadcasts a participant-safe state message plus a live scoreboard via the API Gateway Management API. Room/connection/player rows live in the existing single DynamoDB table under new `ROOM#`/`CONN#` key namespaces with a TTL attribute; the `QUIZ#` items and the whole HTTP API surface are untouched. The frontend adds a `BattlePage` view (no new deps — native `WebSocket`) reachable from the home screen.

**Watch for:** a host network blip permanently ends the game because `$disconnect` unconditionally flips the room to `finished` with no reconnect/grace path (confirmed); the join-by-name duplicate check is a non-atomic read-then-write that two simultaneous joiners can both pass (likely); and `nextQuestion` control transitions have no per-transition idempotency guard, so a double-fire can skip a reveal or a question (likely). The security-critical invariants hold: `answerIndex` is never placed in any broadcast, and host control actions verify the Cognito id token (iss/aud/exp/RS256) server-side (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The design is server-authoritative in the way this feature needs: participants send only an `answerIndex`, the server identifies the player from the connection's stored lookup row (not from a client-supplied name), scores against the stored answer, and never returns the correct index. The state machine is factored into a pure `nextGamePhase` plus AWS-touching handlers, and the answer-stripping projection (`toParticipantQuestion`) is a pure helper with a dedicated leak test.

The host trust boundary is enforced by verifying a full Cognito id token inside the Lambda — signature (RS256 against pool JWKS with a key-rotation refresh), `iss`, `aud`, and `exp` — rather than relying on a gateway authorizer (WebSocket `$connect` can't carry the SPA's bearer token cleanly). Control actions additionally check that the token's `sub` matches the room's stored `hostSub`. The `token_use` check is lenient (only rejects a present-but-wrong value), which is worth tightening even though the `aud` check already blocks access tokens.

Lifecycle handling is the weak spot. Host disconnect ends the room immediately and irrecoverably; there is no grace window or host-reconnect reattachment, so a mobile host switching networks kills every participant's game. Answer submission is idempotent per question via a conditional update, but the host-driven phase transitions and the duplicate-name join are not guarded against races.

The additive guarantee is tested: a second WEBSOCKET-protocol API and a second ARM64 Lambda are added, the HTTP API's seven routes and single JWT authorizer are asserted unchanged (scoped by RouteKey / `resourceCountIs` on the authorizer), and the TTL attribute is additive over `QUIZ#` items that omit it. Cost posture is preserved (on-demand table, TTL cleanup, no VPC/NAT, native WebSocket on the client, no new frontend deps).

<summary>Issues (6)</summary>

1. **Host disconnect is fatal and unrecoverable** — `$disconnect` for a host flips the room to `finished` with no grace window or reconnect reattachment; a transient host network drop ends the game for everyone. Add a short grace period, or let a re-authenticated host with matching `hostSub` reattach to an existing room and rebind `hostConnId`.
2. **Join duplicate-name check is racy** — the GetItem-then-Put in `handleJoinRoom` is not atomic; two simultaneous joiners with the same name both pass the check and the second `PutCommand` (no `ConditionExpression`) silently overwrites the first player's row/score. Put the player item with `attribute_not_exists(pk)`/`attribute_not_exists(sk)` and treat the conditional failure as "name taken".
3. **Control transitions lack idempotency guards** — `startGame`/`nextQuestion` read the phase then write with a plain `UpdateExpression` and no `ConditionExpression`; a double-fire (or two host tabs) can double-advance, skipping a reveal or a question. Gate the update with a `ConditionExpression` on the expected current phase (and current question index for `nextQuestion`).
4. **`token_use` accepts a missing claim** — `payload.token_use !== undefined && payload.token_use !== 'id'` permits a token with no `token_use`. Require `token_use === 'id'` outright; the `aud === clientId` check already blocks access tokens, so this is defense-in-depth, but make it explicit.
5. **Player rows/scoreboard are not cleaned on participant disconnect** — `handleDisconnect` removes the connection rows but leaves the `PLAYER#` row, so a disconnected participant lingers on the live scoreboard until TTL. Decide whether that is intended (persist score across reconnect) or prune the player; either way document it.
6. **Networked-host verification needed** — builds/tests could not run in this sandbox (INTEGRATIONS_ONLY). On a networked host, run `npm test` (jest), `npx cdk synth`, and a `vite build`, and smoke-test a real host+participant round including host token expiry mid-game.

### Server-authoritative scoring and the answerIndex boundary

The security-critical invariant — the correct answer never reaches a browser — is enforced structurally rather than by discipline. The stored question is projected through `toParticipantQuestion`, which returns exactly `{ n, text, options }`, and `buildStateMessage` only ever embeds that projection; `answerIndex` has no path into any `PostToConnection` payload. The `answerAck` sent back to a submitter carries only `{ n, correct }`, not the index. The pure projection has a dedicated test that both checks `hasOwnProperty` and does a `JSON.stringify(...).not.toContain('answerIndex')` deep scan, mirroring the HTTP handler's `toPublicQuestions` test.

Scoring is fully server-side: `handleSubmitAnswer` ignores any client-supplied name/room, resolves the player from the connection lookup row (`getConnLookup`), loads the stored question, and compares server-side via `scoreSingleAnswer`. A participant therefore cannot score for another player's name, cannot learn the answer, and cannot inflate their own score beyond one point per question.

### Host trust boundary via in-Lambda JWT verification

Because a WebSocket `$connect` can't carry the SPA's bearer token the way an HTTP authorizer expects, the host boundary is enforced inside the handler: `verifyHostToken` splits the JWT, requires `alg === RS256`, checks `exp`, `iss === COGNITO_ISSUER`, and `aud === COGNITO_CLIENT_ID`, then verifies the RS256 signature against the pool JWKS built into a `crypto.createPublicKey({ format: 'jwk' })`. JWKS is cached at module scope with a single refresh-and-retry on an unknown `kid`, handling key rotation without hammering the endpoint. `requireHostForRoom` then binds the action to the room by requiring `payload.sub === room.hostSub`, so a valid admin token for a *different* admin cannot drive someone else's room.

Two observations. The `token_use` guard is `payload.token_use !== undefined && payload.token_use !== 'id'`, which lets a token with the claim absent through; Cognito id tokens always include it, and the `aud` check already rejects access tokens (they carry `client_id`, not `aud`), so this is not exploitable as written, but it should be tightened to `=== 'id'` so the invariant doesn't depend on the `aud` check alone. Separately, `verifyHostToken` returns `null` (→ generic "unauthorized") when `COGNITO_ISSUER`/`COGNITO_CLIENT_ID` are unset; that fails closed, but means a misconfigured deploy looks like an auth failure rather than a config error — worth a log line.

### Host disconnect ends the game with no recovery

```
host WS drops  ->  $disconnect  ->  removeConnection(host)
                                     room.phase != finished  ->  SET phase = finished
                                     broadcastState  ->  all participants see "finished"
```

`handleDisconnect` treats any host disconnect as game-over: it unconditionally flips a non-finished room to `finished`. There is no grace window and no path for a host who reconnects (new `connectionId`) to reattach to the room — `createRoom` always mints a new room, and no action rebinds control to an existing room's `hostConnId`. A host on mobile who briefly loses connectivity, or whose laptop sleeps, permanently ends the session for every participant mid-game. For a "battle" whose whole point is a shared live session, this is the most impactful correctness gap. A short TTL-based grace window, or allowing a re-authenticated host (matching `hostSub`) to reattach to and resume an existing room, would address it.

### Per-question idempotency vs. unguarded control transitions

Answer submission is idempotent: the conditional update `attribute_not_exists(answeredForQuestion) OR answeredForQuestion < :q` with `score = score + :inc` (inc 0 when wrong) means a player can affect a given question exactly once, and a `ConditionalCheckFailedException` is swallowed as a duplicate. A wrong answer still advances `answeredForQuestion`, locking the player out of retrying that question — the intended "one shot per question" behavior.

The host control transitions do not get the same treatment. `handleStartGame` and `handleNextQuestion` read the room, compute the next phase with the pure `nextGamePhase`, then write with a plain `UpdateExpression` and no `ConditionExpression`. Because the WebSocket handler can run concurrent invocations, two rapid `nextQuestion` clicks (or two host tabs) can both read `in_question` and both write `between`, or read stale state and double-advance — skipping a reveal or an entire question. The blast radius is limited to a single host misclicking, but the fix is cheap: guard each transition write with a `ConditionExpression` asserting the expected current `phase` (and `currentQuestion` for `nextQuestion`), so a losing racer no-ops instead of double-stepping.

### Room/connection/player data model and fan-out

The model reuses the single table: `ROOM#<id>/META`, `ROOM#<id>/CONN#<connId>`, `ROOM#<id>/PLAYER#<name>`, and a reverse `CONN#<connId>/META` lookup so a disconnect or answer can resolve room+role from just the connection id. Broadcast fan-out queries all `CONN#` rows for the room and `PostToConnection`s in parallel, cleaning up on `GoneException`. Note the asymmetry: `handleDisconnect` prunes the connection/lookup rows yet leaves the `PLAYER#` row intact, so a participant who closes their tab keeps appearing on the live scoreboard until the 6h TTL fires. There is no reconnect-by-name path either, so in practice it's a ghost entry — worth an explicit decision (persist-across-reconnect vs. prune).

Fan-out cost is O(connections) `PostToConnection` calls per state change, and every `submitAnswer` triggers a full `broadcastState` (which re-queries connections + players and, in `in_question`, re-fetches the quiz's questions). For a classroom-sized room this stays within the cost-minimal posture; for large rooms the re-fetch of all questions on every answer is the first thing that would need caching, but that's a scale concern, not a v1 blocker.

### Additive guarantee and cost posture

The tests pin the additive guarantee down. A second API Gateway v2 API is added with `ProtocolType: WEBSOCKET` and the test asserts exactly two v2 APIs plus the seven HTTP routes matched by RouteKey (`GET /api/quizzes`, …), so a regression that dropped or altered an HTTP route would fail. The JWT authorizer test still asserts `resourceCountIs('AWS::ApiGatewayV2::Authorizer', 1)` — the WebSocket API adds none — and public/admin route authorization types are unchanged. The DynamoDB TTL is added on attribute `ttl`; `QUIZ#` items omit it and are never expired, so single-player/admin/history/seed flows are unaffected. The Cognito app client gains `/index.html` callback/logout URLs alongside the retained `/admin.html` ones, under the same `adminAppBaseUrl` + localhost gating, which is what lets the host reuse the existing Hosted UI from the public app.

Cost posture is preserved: on-demand table, TTL cleanup, a 256MB/10s ARM64 Lambda, no VPC/NAT, and the client uses the native browser `WebSocket` so frontend deps stay exactly `react` + `react-dom` with no lockfile churn. `@aws-sdk/client-apigatewaymanagementapi` is added to `dependencies` but bundled `external` (`@aws-sdk/*`), relying on the Node 22 runtime's bundled SDK — consistent with how the existing Lambda treats the other SDK clients.

### Not tested

The pure helpers are well covered (state machine lifecycle, scoreboard sort/tiebreak, room-id alphabet, join validation, answer-strip leak). Not covered — and not unit-testable without integration harnessing — is the AWS-touching behavior where the flagged risks live: host-disconnect-ends-game, the join-name race, the control-transition races, and JWT verification (signature/exp/iss/aud paths). `verifyHostToken` in particular has zero tests; it's security-critical and pure enough (given an injected JWKS/token) to warrant unit coverage of the reject paths (bad alg, expired, wrong iss/aud, bad signature, unknown kid). Because builds/tests couldn't run in this sandbox, run jest, `cdk synth`, and `vite build` on a networked host and smoke-test a full host+participant round including a host token expiring mid-game.
