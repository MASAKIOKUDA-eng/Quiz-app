# Realtime battle — v1 review findings fix (v2)

The fix commit (`3999c14`) reworks the realtime battle lifecycle and hardens its concurrency and auth boundaries in response to the six v1 `NEEDS_CHANGES` findings. Host disconnect is now a recoverable "away" state (hostConnId cleared, phase preserved) with a new `reattachRoom` action for a re-authenticated host to rebind; the duplicate-name join is now an atomic conditional Put; `startGame`/`nextQuestion` carry conditional guards on the expected phase/question; `token_use` must be exactly `id`; participant disconnect prunes the `PLAYER#` row; and a pure `validateTokenClaims` helper was extracted with ten reject-path unit tests. All six findings are resolved and the security/additive invariants are intact.

**Watch for:** nothing blocking. The reattach model correctly avoids the stale-disconnect clobber via a `hostConnId = :thisConn` guard keyed on the old connection (confirmed); a stale/half-open old host socket leaves a `CONN#` row that is reaped lazily via `GoneException` on the next broadcast rather than eagerly (confirmed, benign). Builds/tests could not run here (INTEGRATIONS_ONLY) — jest, `cdk synth`, and `vite build` must be run on a networked host (confirmed environment limit).

**Verdict**: APPROVED

## High-level view

The host-away/reattach model is sound. `$disconnect` for a host no longer flips the room to `finished`; it clears `hostConnId` to the `''` sentinel and keeps the phase, and that clear is guarded by `ConditionExpression hostConnId = :thisConn` where `:thisConn` is the *disconnecting* connection id. A reattach that already rebound `hostConnId` to a new connection therefore cannot be clobbered by a late-firing stale disconnect — the guard simply no-ops. `reattachRoom` re-writes both the host `CONN#` row and the reverse lookup row for the new connection, so the reattached host is a broadcast target again and its control panel is restored via a `roomCreated`-shaped reply.

The atomic join is correct: the `PLAYER#` row is now written first with `attribute_not_exists(pk) AND attribute_not_exists(sk)`, and `ConditionalCheckFailedException` surfaces as "name already taken". Writing the player row before the connection/lookup rows means a lost name race leaves no orphan connection rows. Participant disconnect deletes the `PLAYER#` row (freeing the name), which is consistent with the atomic-claim model.

Control-transition races are closed. `startGame` guards on `phase = 'lobby'`; `nextQuestion` guards on both `phase` and `currentQuestion`; a losing racer catches the conditional failure and re-broadcasts instead of double-stepping.

The auth boundary is unchanged and slightly tightened: `token_use` must now be exactly `id`, `reattachRoom` requires a verified token whose `sub` matches `room.hostSub` (participants remain unauthenticated), and the pure claim checks are now unit-tested. The `answerIndex` boundary is untouched — it exists only on `StoredQuestion` and is dropped by `toParticipantQuestion`, with no path into any broadcast. The change is additive: one new WebSocket route (`reattachRoom`) added to the stack and both the stack route-list test and the WS action switch, HTTP routes/authorizer/single-player/admin/history flows untouched, and frontend deps unchanged (native `WebSocket`).

### Host-away/reattach: the disconnect-vs-reattach race is correctly ordered

The v1 fatal-disconnect finding is resolved by turning host disconnect into a recoverable state rather than a terminal one. `handleDisconnect` for a host now issues `SET hostConnId = :empty` guarded by `ConditionExpression hostConnId = :thisConn` (`:thisConn` = the disconnecting connection id), catching and swallowing `ConditionalCheckFailedException`. The interesting case is a rapid disconnect *after* a reattach:

```
old host socket drops                 host re-auths on a new socket
   │                                     │
   │ (network delay before $disconnect)  reattachRoom:
   │                                        SET hostConnId = <newConn>   (unconditional)
   │                                        PutCommand CONN#<newConn>
   │                                        PutCommand CONN_LOOKUP<newConn>
   ▼
$disconnect (old):
   SET hostConnId = '' IF hostConnId = <oldConn>   -> condition FAILS -> no-op
```

Because the guard pins on the *old* connection id, a late stale disconnect cannot clear a freshly-rebound `hostConnId`. The reverse order (disconnect clears to `''`, then reattach sets the new conn) is also fine — reattach's `SET` is unconditional and wins. The one loose thread is the old host `CONN#` row: `reattachRoom` does not call `removeConnection` for the prior connection, so if the old socket never cleanly disconnects the stale row lingers until its `GoneException` surfaces on the next broadcast (then it's cleaned up). This is harmless — one wasted `PostToConnection` — but is the specific thing to observe during a real half-open-socket reconnect.

`buildStateMessage` reports `hostConnected: typeof room.hostConnId === 'string' && room.hostConnId.length > 0`, which reads the `''` sentinel as `false` and any real connection id as `true` — consistent with the clear/rebind writes.

### Atomic join and name-freeing consistency

`handleJoinRoom` drops the racy `GetItem`-then-`Put` and writes the `PLAYER#` row first under `attribute_not_exists(pk) AND attribute_not_exists(sk)`, translating the conditional failure into "name already taken in this room" and re-throwing anything else. Two simultaneous same-name joiners can no longer both succeed. Ordering the player Put before the connection/lookup Puts means a lost race returns before any orphan connection rows are written. Participant `$disconnect` deletes the `PLAYER#` row (best-effort, TTL backstop), which frees the name for reuse and keeps the live scoreboard free of ghost entries — the explicit decision documented in code and README, and consistent with the atomic name-claim. `pk`/`sk` are not DynamoDB reserved words, so the bare `attribute_not_exists` usage is valid without `ExpressionAttributeNames` (the existing key queries alias them defensively; the new condition does not need to).

### Control-transition guards

`handleStartGame` now writes under `ConditionExpression phase = :expected` (`:expected = 'lobby'`); `handleNextQuestion` writes under `phase = :expectedPhase AND currentQuestion = :expectedCq` pinned to the values read at the top of the handler. A double-fire (two rapid clicks / two host tabs / concurrent invocations) that loses the race catches `ConditionalCheckFailedException` and re-broadcasts current state instead of double-advancing past a reveal or a question. `phase` and `currentQuestion` are not reserved words, so bare usage is valid. This mirrors the already-correct per-question idempotency on `submitAnswer`.

### Auth boundary: token_use tightened, reattach bound to hostSub, claim checks unit-tested

`validateTokenClaims` is now a pure exported helper checking `alg === 'RS256'`, a non-empty `kid`, numeric non-expired `exp` (with injectable `now`), `iss`, `aud === clientId`, `token_use === 'id'` (no longer lenient about a missing claim), and a non-empty `sub`, returning `{ sub, kid }` on success. `verifyHostToken` delegates the claim checks to it and keeps the RS256/JWKS signature verification (with the key-rotation refresh-and-retry) in the AWS-touching layer, then returns `claims.sub`. A config-missing log line was added so a misconfigured deploy is distinguishable from a genuine auth failure while still failing closed. `reattachRoom` runs the full `verifyHostToken` and then requires `room.hostSub === hostSub`, so only the room's true host — not another valid admin — can rebind control, and participants remain unauthenticated (name + roomId only). The ten new reject-path tests cover bad alg, missing/empty kid, expired/missing/non-numeric exp, iss mismatch, aud mismatch, missing token_use, non-`id` token_use, and missing/empty sub — the security-critical rejects that were untestable in v1.

### answerIndex boundary and additive guarantee preserved

`answerIndex` appears only on the server-side `StoredQuestion` type and is stripped by `toParticipantQuestion`; no new code path (reattach's `roomCreated` reply, the `hostConnected` field, the scoreboard) carries it into a broadcast, and `answerAck` still returns only `{ n, correct }`. The change is additive: exactly one new WebSocket route (`reattachRoom`) is added to the stack's action loop, and both the WS action `switch` and the stack test's `wsRouteKeys` list were updated in lockstep, so the route-list assertion stays green. The stack test asserts route *presence* (`hasResourceProperties` per key) rather than a hardcoded count, so adding a route does not create a stale count assertion. HTTP routes, the single JWT authorizer, single-player/admin/history/seed flows, and `package.json` frontend deps (react + react-dom, native WebSocket, no lockfile churn) are untouched.

### Frontend contract

`StateMessage`/`LiveState` gained `hostConnected`, mapped through in both host and participant `state` handlers. The participant view shows a host-away note gated on `!live.hostConnected && live.phase !== 'finished'`, so it does not fire on a normally finished game. The host auto-reattach reads `roomIdRef`/`idTokenRef`, both assigned on every render (`roomIdRef.current = roomId`), so `onOpen` sees current values rather than a stale closure; the send is guarded by `if (currentRoom && currentToken)`, making the initial pre-room connect a no-op. `OutboundActionMap` gained `reattachRoom`, keeping `send()` type-safe.

### Not tested (here)

The pure `validateTokenClaims` reject paths are now unit-covered. Still exercised only by the networked smoke test, not unit tests: the reattach DynamoDB writes and the disconnect conditional-clear race, the atomic-join conditional path, and the RS256 signature/JWKS verification. Run jest, `cdk synth`, and `vite build` on a networked host and smoke-test a host-drop-then-reattach round (including a token expiring mid-game and a half-open-socket reconnect) — none of this could execute in the INTEGRATIONS_ONLY sandbox.
