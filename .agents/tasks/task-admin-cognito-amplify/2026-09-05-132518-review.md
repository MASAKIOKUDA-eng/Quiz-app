# Original AWS-architecture seed quizzes, Cognito-guarded admin write API, and Amplify Hosting rewire (v1)

Replaces the placeholder seed data with two original Japanese AWS-architecture quiz sets (a 12-question `aws-architecture` set that satisfies the ≥10 requirement plus a 6-question `aws-serverless` set), adds a Cognito-authenticated `POST /api/admin/quizzes` route so operators can register custom quizzes through a new Hosted-UI-backed admin SPA, and moves frontend hosting off S3+CloudFront onto Amplify Hosting (hosting only). The write path reuses the same single-table item shapes as the seeder via a shared `buildQuizItems`, and input validation lives in an exported pure `validateAndNormalizeQuizInput` that the admin page mirrors client-side. The public GET/submit routes stay open; only the admin write route carries the JWT authorizer. All four user requirements are met and the security-critical `answerIndex` stripping (`toPublicQuestions`) is untouched.

Watch for: the admin route authorizes **any** authenticated pool user with no group/role gate (confirmed) — acceptable only because self-signup is disabled and operators create every user; the production Cognito app client keeps `http://localhost:8080/admin.html` in its callback/logout URLs (confirmed); and the Amplify domain, Cognito callback URLs, and `allowOrigins` are all deferred to manual post-deploy wiring (confirmed), so a fresh deploy will not have a working login round-trip until an operator updates them.

**Verdict**: APPROVED

## High-level view

The seed rewrite delivers original, reasoning-oriented AWS-architecture questions in Japanese, and a build-time test asserts at least one set has ≥10 questions so a future shrink fails CI. Content correctness of individual answer keys is not machine-verifiable and was spot-checked only.

The admin write path is a single new authenticated route on the existing HTTP API. Validation is a pure exported function reused by unit tests and mirrored in the browser; persistence shares `buildQuizItems` with the seeder so both stay structurally in sync. Authorization is coarse: the JWT authorizer proves the caller is a pool member but nothing distinguishes an admin from any other user — safe here only because self-signup is off.

Cognito is a self-signup-disabled user pool with a public (secretless) SPA client and a Hosted UI prefix domain derived from the account id. The SPA uses the implicit grant, reads `id_token` from the URL fragment, and sends it as a Bearer token. The authorizer validates `aud` against the client id, which matches the id_token — consistent, but it means the access token would not work if the client ever switched to it.

The hosting move to Amplify makes API calls cross-origin, which is why CORS now allows the `authorization` header. Several values (`allowOrigins`, Cognito callback/logout URLs, the SPA's `API_BASE`/`COGNITO_*`) are intentionally not knowable at synth time and are wired manually or injected by `amplify.yml` at build. The trade-off is documented, but the seams are the most likely source of a broken first deploy.

### Original seed content and the ≥10 guard

The two seed sets are original reasoning questions (on-demand vs provisioned capacity, gateway VPC endpoints to avoid NAT idle cost, SNS fan-out, HTTP API vs REST API cost, Graviton, Multi-AZ failover, OAC, idempotent SQS consumers, least-privilege IAM, Aurora Serverless v2, Kinesis ordering) rather than lifted exam material, satisfying requirements (1), (2), and the "AWS architecture implementation" clarification. The `aws-architecture` set has 12 questions; `aws-serverless` has 6.

The seed-validity test asserts `Math.max(...questions.length) >= 10` rather than pinning the primary quiz, so the ≥10 invariant survives even if question order or set membership changes. What it cannot check is whether each `answerIndex` actually points at the correct option; that is content, not structure, and was only spot-checked here. The distractors are plausible enough that a wrong key would pass every test, so answer keys deserve a human read before shipping.

### Admin write route: validation, collision, and coarse authorization

The route reuses `validateAndNormalizeQuizInput` (pure, exported, unit-tested) for the untrusted payload and `buildQuizItems` (shared with the seeder) for persistence, so the write path and seed path cannot drift in item shape. A pre-write `getQuizItems` check returns 409 on an existing `quizId`, and validation failures return 400.

The authorization gap is the one thing worth a decision: the JWT authorizer proves the caller holds a valid token issued by this pool for this client, but the handler does no further check — every authenticated user is an admin. This is safe *only* because `selfSignUpEnabled: false` means an operator provisions every account. If that ever changes, or if the pool is reused for a non-admin audience, the write route is open to all of them. A Cognito group claim check (`cognito:groups` contains `admins`) in the handler would make the intent explicit and defend against pool reuse. At minimum the README should state that pool membership *is* the admin grant.

```
browser (id_token) --Bearer--> HttpJwtAuthorizer (aud == clientId, iss == pool)
                                        |
                                        v
                              handler POST /api/admin/quizzes
                                 validate -> 400
                                 collision -> 409
                                 buildQuizItems -> BatchWrite -> 201
```

### Cognito posture and the implicit-grant token choice

The authorizer's `jwtAudience` is the client id, which matches the `aud` of an id_token (an access token's `aud`/`client_id` shape differs), so the id_token the SPA sends is the right token and the two sides are consistent. This couples the design to the id_token specifically; a future switch to the access token would require changing the authorizer audience config.

The client keeps both the parameterized `adminAppBaseUrl` callback and a hardcoded `http://localhost:8080/admin.html` in `callbackUrls`/`logoutUrls`, so a production pool trusts a localhost redirect target. Low severity for an implicit-grant SPA that pins its own `redirect_uri`, but the localhost entries should be dropped for real deployments rather than shipped by default.

### Hosting move and the manual wiring seams

Dropping S3+CloudFront in favor of Amplify Hosting removes the old distribution-wide 403/404→index.html rewrite that clobbered the API's 4xx JSON. The consequence is cross-origin API calls, handled by adding `authorization` to `allowHeaders`. Since the SPA sends a Bearer token (not cookies), `allowOrigins: ['*']` without credentials is valid for HTTP API CORS and does not need narrowing to function — but narrowing to the real Amplify domain is still worth doing once known, as the code comment notes.

The fragile part is that three things are unknowable at synth and deferred to humans/build: `allowOrigins`, the Cognito callback/logout URLs (defaulted to localhost via `adminAppBaseUrl`), and the SPA runtime config (`API_BASE`/`COGNITO_DOMAIN`/`COGNITO_CLIENT_ID`, injected by `amplify.yml` from Amplify env vars). A first deploy will synth cleanly and still have a broken login round-trip until an operator updates the app client callback URLs with the Amplify domain and sets the Amplify env vars. The README covers these steps; an explicit ordered post-deploy checklist would reduce the chance of a half-wired stack.

### Client-side validation mirror

`collectPayload` in admin.js recomputes `answerIndex` against the *non-empty* option list so skipped blank option rows don't desync the correct-answer index — a real edge case handled correctly. The server revalidates, so the client mirror is UX, not a trust boundary. `postJson` maps 401 to a re-login prompt and clears the stored token; 403 is surfaced but, given the coarse authorization above, 403 is not currently reachable.

### Test coverage

Handler tests add thorough `validateAndNormalizeQuizInput` cases (bad body, missing/empty title, empty/short options, out-of-range/non-integer `answerIndex`, bad and auto-generated `quizId` including a non-ASCII title yielding a non-empty slug) and seed-validity assertions (≥10 questions, every field well-formed, unique URL-safe ids). CDK tests assert the four routes, the JWT authorizer on only the admin route, public routes with `AuthorizationType: NONE`, self-signup disabled, a secretless client, the Hosted UI domain, CORS allowing `authorization`, and the removal of CloudFront/S3 and the `CloudFrontDomain` output.

Not tested: the handler's admin branch end-to-end (validate→409/201 against a mocked DynamoDB), so the 409 collision path and the BatchWrite persistence are exercised only indirectly through the pure helpers. No test asserts the id_token/authorizer audience contract. The client-side `answerIndex` recomputation in `collectPayload` has no test (browser-only logic), so its blank-row edge case is unverified outside manual use.
