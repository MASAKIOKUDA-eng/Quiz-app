### `tsc -b` no longer rejects the composite node project

The v1 blocker was `frontend/tsconfig.node.json` carrying both `composite: true` and `noEmit: true`; a project referenced under `tsc -b` may not disable emit, so `npm run build` (`tsc -b && vite build`) failed before Vite ran. The fix removes `noEmit`, keeping `composite: true`:

```jsonc
// frontend/tsconfig.node.json (after 287a008)
{ "compilerOptions": { "composite": true, ..., "strict": true }, "include": ["vite.config.ts"] }
```

Reproduced both directions with the sandbox's global `tsc` (5.x). Re-adding `noEmit` to the node config brings the error back:

```
tsconfig.json(28,18): error TS6310: Referenced project '.../frontend/tsconfig.node.json' may not disable emit.
```

The shipped config produces zero `TS63xx` configuration-class errors. The only diagnostics that remain are missing-module errors — `Cannot find module 'react' / 'vite' / '@vitejs/plugin-react'`, `Cannot find name '__dirname'`, `@types/node` — all of which stem from dependencies not being installed (npm 403), not from the project-reference graph. Under the pinned `typescript@~5.5.4` the config-error code was expected to surface as TS6379 ("Composite projects may not disable emit"); the sandbox `tsc` reports it as TS6310 instead — same failure class, same non-zero exit, and the fix clears both wordings. The app `tsconfig.json` keeps `noEmit: true` and is correctly *not* composite (it is the root of the `-b` graph, not a referenced project), so the composite/emit constraint does not apply to it.

### handleLogin guard matches the old admin.js intent

`AdminPage.handleLogin` now reads `COGNITO_DOMAIN`/`COGNITO_CLIENT_ID` from `../config` — the same normalized values `auth.ts` feeds into `loginUrl()` (domain with trailing slash stripped, client id defaulted to `''`). When either is empty it sets an error status and returns before redirecting:

```
Cognito の設定（VITE_COGNITO_DOMAIN / VITE_COGNITO_CLIENT_ID）が未設定です。
frontend/.env（Amplify の環境変数）を確認してください。
```

This restores the diagnostic the old `admin.js` showed when config was missing, and points the operator at the exact env-var names and the file/console location. Because the guard checks the identical inputs `loginUrl()` consumes, no state can pass the guard and still build a malformed URL. With both values populated (the deployed case, where Amplify injects them) the function reaches the unchanged `window.location.assign(loginUrl())`.

### Scope: only frontend files changed, backend untouched

The fix commit `287a008` changes five paths: `amplify.yml`, `frontend/src/pages/AdminPage.tsx`, `frontend/tsconfig.node.json`, plus the v1 review file and `task.json` (metadata). Across all three frontend-rebuild commits the changed set is confined to `frontend/`, `README.md`, `amplify.yml`, `.gitignore`, and task metadata. The CDK/Lambda/test files were introduced by earlier backend commits (`bin/quiz-app.ts` at `e13df2c`, `lib/quiz-app-stack.ts` at `80303b8`, `lambda/index.ts` and `test/handler.test.ts` at `f01e753`) and are not modified by the frontend work, so the API contract, admin validation semantics, Cognito flow, and `/admin.html` callback-URL matching verified in v1 stand unchanged.
