# Admin quiz edit/delete UI and frontend polish (v1)

The admin page gains a management surface: an authenticated list of quizzes, a full-replace edit flow, and a confirm-guarded delete, on top of the existing create form. The API client grows three typed admin methods (`getAdminQuiz`, `updateQuiz`, `deleteQuiz`) that were extracted alongside `createQuiz` into a shared `adminRequest<T>` helper, so all admin calls share one auth/error contract. The visual layer (`styles.css`) is reworked — palette, spacing, buttons, cards, score ring, dark mode, and motion — and `HomePage` adds a display-only encouragement line plus softened microcopy. The change is frontend-only; the backend routes it calls (`/admin/quizzes/{quizId}` GET/PUT/DELETE) live in an unmerged companion PR, so the edit/delete paths cannot succeed end-to-end against `main` yet.

Watch for: the create success path shows a result card that hides the form, and the edit/create flow shares one `collectPayload` whose Japanese validation strings and answerIndex computation had to stay byte-identical — both verified below (confirmed). The sandbox is registry-locked (npm 403), so `tsc`/`vite build` could not be run; this review is read-only (see note).

**Verdict**: APPROVED

## High-level view

The admin methods route through a single `adminRequest<T>` helper that reproduces the original `createQuiz` status handling exactly — `Bearer` auth, 401→`AuthError`, 403→`権限がありません`, JSON-message preference, and the non-JSON guard — with `content-type` now set only when a body is present, which is the correct distinction for GET/DELETE. `createQuiz`'s externally observable behavior is unchanged.

Edit mode reconstructs the form from the admin GET by marking the option row at `answerIndex` as correct; because server options are all non-empty, the DOM index equals the stored index, so re-running `collectPayload` on untouched options yields the same `answerIndex`. Edit fixes the quizId (read-only input, path-derived, excluded from the body and from quizId validation) and submits via PUT; create is untouched and still POSTs with the optional `/^[a-z0-9-]+$/` quizId.

The 401 path is now centralized in `handleAuthError` (clearToken + reset + re-login prompt) and used across create, edit, delete, and list; 403 continues to surface `権限がありません` from the client. Delete prompts `window.confirm` before calling DELETE, resets the form if the quiz being edited is the one deleted, and refreshes the list on success.

HomePage's scoring, `-1`-for-unanswered answers, aria-labels, and the `--percent` conic-gradient score ring are untouched; the new `encouragement(percent)` is display-only and keyed off the same percent used for the ring. No new dependencies (still react + react-dom), Vite's real `/admin.html` + `/index.html` structure is intact, and backend, `amplify.yml`, `auth.ts`, and `config.ts` are untouched.

## adminRequest extraction preserves createQuiz semantics

The original `createQuiz` body was lifted verbatim into `adminRequest<T>(path, method, idToken, body?)`; the 401→`AuthError`, 403→`Error('権限がありません')`, non-ok JSON-message-else-generic, and ok-but-non-JSON→`UNEXPECTED_NON_JSON` branches are unchanged, only the return cast became generic. The one deliberate behavioral difference is header construction: `content-type: application/json` is now conditional on `body !== undefined`, so `getAdminQuiz`/`deleteQuiz` (no body) don't advertise a JSON content type while `createQuiz`/`updateQuiz` still do. Id-scoped paths use `encodeURIComponent(quizId)` — the right default for ids arriving from the list rather than the `[a-z0-9-]`-constrained create input.

## Edit reconstruction and the shared collectPayload

`enterEditMode` rebuilds `QuestionState` from `getAdminQuiz`, setting `isCorrect: idx === q.answerIndex`. The round-trip invariant holds: server options are all non-empty, so the DOM option index equals the collected index, and `collectPayload`'s answerIndex computation (skip empty options, count the checked row's position among non-empty ones) returns the same `k` it was built from when options are left unedited.

`collectPayload` is reused for both modes. Its validation strings were diffed against `origin/main` and are byte-identical — the full set (`タイトルを入力してください。`, `問題を 1 つ以上追加してください。`, `問題 N の問題文を入力してください。`, `問題 N には空でない選択肢を 2 つ以上入力してください。`, `問題 N の正解を選択してください。`, `問題 N の正解は空でない選択肢を選んでください。`, `クイズ ID は半角英小文字・数字・ハイフンのみ使用できます。`) matches. The only structural change is that the quizId trim/regex/assignment block is now gated behind `mode.kind === 'create'`, so edit mode neither validates nor sends a body quizId — correct, since the path carries the id and the server ignores a body quizId.

Edit submit calls `updateQuiz(editingQuizId, ...)` (PUT) where `editingQuizId` is captured from `currentMode.quizId` rather than the mutable `quizId` state, so an in-flight edit targets the loaded quiz, not whatever the read-only field shows. The edit-success status line renders `res.questionCount` behind a `typeof === 'number'` guard that is redundant against the typed response — harmless, mirrors the create card.

## Auth-error centralization across paths

`handleAuthError` folds the previously inline 401 handling (`clearToken` + `setIdToken(null)` + `setExpiresAt(0)` + `ログインが必要です（認証エラー）`, string preserved from base) into one function that create/edit/delete/list all funnel `AuthError` into. 403 is not intercepted in the component; it arrives as a plain `Error('権限がありません')` from the client and renders through `errorMessage(err)` in the status line, consistent across all three write paths. `enterEditMode` and `handleDelete` both guard on `!isAuthenticated || !idToken` up front and route to `handleAuthError`, so a stale-session click fails closed rather than firing an unauthenticated request.

## Delete confirm and form-state coherence

`handleDelete(quizId, title)` calls `window.confirm('「' + title + '」を削除します。よろしいですか？')` and returns early on cancel, so DELETE only fires on explicit confirmation. On success it refreshes the list and, when the deleted quiz is the one currently open in edit mode (`mode.kind === 'edit' && mode.quizId === targetQuizId`), resets the form to create mode — avoiding a dangling edit session pointed at a deleted quiz. Non-matching deletes leave an active edit session intact.

## Create result card interaction

On create success the component sets `result` and the render swaps the form for the result card. The quiz list sits above and stays mounted, so 編集/削除 remain reachable and 編集 clears `result` back into edit mode. The rough edge: creating a second quiz in a row requires pressing 新規作成 (`resetToCreate`); there is no direct create→create continuation. Worth confirming this matches intended UX. (confirmed)

## Scope and build note

`git diff origin/main...HEAD --name-only` touches only `README.md`, `frontend/src/api.ts`, `frontend/src/pages/AdminPage.tsx`, `frontend/src/pages/HomePage.tsx`, and `frontend/src/styles.css`. Backend (`lambda/`, `lib/`, `test/`), `amplify.yml`, `auth.ts`, `config.ts`, and `frontend/package.json` are untouched; dependencies remain react + react-dom with no lockfile added. The score ring keeps the exact `--percent` conic-gradient mechanism HomePage feeds via inline style, and animations are guarded under `prefers-reduced-motion: reduce`; `encouragement(percent)` is keyed off the same `round(score/total*100)` as the ring and does not touch scoring.

The sandbox is registry-locked (npm install returns 403), so `tsc --noEmit` and `vite build` could not be executed. Type usage was checked by reading and is consistent; unbuilt code is not treated as a defect, but a type-check/build on a networked runner before merge is advisable.
