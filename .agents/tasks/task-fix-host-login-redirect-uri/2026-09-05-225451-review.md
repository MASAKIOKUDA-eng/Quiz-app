# Guard adminAppBaseUrl against a trailing slash to keep the ROOT redirect exact (v2)

This pass reviews the follow-up commit (`3126205`) that addresses v1's non-blocking trailing-slash footgun. The v1 fix canonicalized the host `redirect_uri` to ROOT (`origin + '/'`) and paired it byte-for-byte with the CDK app client; v1 flagged that `adminAppBaseUrl` is concatenated raw as `${value}/`, so an operator-supplied base URL ending in `/` would produce `//` and reintroduce `redirect_mismatch`, and that a JS `.replace()` on the `.valueAsString` token would be a silent no-op. The coder closed this at the source by adding an `allowedPattern` (`^(https?://)[^\s]*[^/\s]$`) plus a `constraintDescription` to the `adminAppBaseUrl` CfnParameter, so CloudFormation rejects a trailing slash (and scheme-less values) at deploy time, and added a jest test that reads the synthesized `AllowedPattern` and asserts it accepts trailing-slash-free http(s) origins while rejecting trailing slashes and scheme-less hosts. README and code comments were updated to state the no-trailing-slash requirement.

Watch for: the `AllowedPattern` accepts the default value `http://localhost:8080`, so a default-parameter synth/deploy is not broken (confirmed). The v1 byte-for-byte redirect correspondence is unchanged and nothing unrelated was touched in this commit (confirmed). The sole v1 finding acted on is resolved; its companion (host token captured only after entering the host view) remains intentionally out of scope.

**Verdict**: APPROVED

## High-level view

The guard lives on the `adminAppBaseUrl` CfnParameter rather than in synth-time JS, which is the correct layer: `.valueAsString` is a token, so validation has to run in CloudFormation. The `allowedPattern` requires an `http(s)://` scheme and forbids a trailing `/`, the exact shape the raw concatenation depends on to avoid a doubled slash in the ROOT entry.

The regex is self-consistent with its own default. `^(https?://)[^\s]*[^/\s]$` accepts `http://localhost:8080` (the parameter default) and `https://main.d2uwsqpk41y7so.amplifyapp.com`, and rejects both with a trailing slash plus a scheme-less `main.<...>.amplifyapp.com`. Because the default satisfies the pattern, a deploy or synth that does not override the parameter still passes CloudFormation validation.

The new test reads the synthesized `AllowedPattern` and exercises it against accept and reject cases, so removing or weakening the pattern breaks the test. The v1 redirect contract (frontend `adminRedirectUri()`/`publicRedirectUri()` mirrored by the CDK callback/logout URLs) is byte-for-byte identical to the prior pass, and the JWT authorizer, WebSocket API, and scoring paths are untouched.

### AllowedPattern accepts the default and rejects the footgun

The pattern `^(https?://)[^\s]*[^/\s]$` is an anchored `http://` or `https://` scheme, then any run of non-whitespace, then a final non-slash non-whitespace character before end-of-string. The trailing `[^/\s]$` is what forbids a trailing slash: a value ending in `/` cannot satisfy the last-character class.

```
http://localhost:8080                          scheme ok, ends '0'  -> ACCEPT (this is the DEFAULT)
https://main.d2uwsqpk41y7so.amplifyapp.com     scheme ok, ends 'm'  -> ACCEPT
http://localhost:8080/                          ends '/'             -> REJECT
https://main.d2uwsqpk41y7so.amplifyapp.com/     ends '/'             -> REJECT
main.d2uwsqpk41y7so.amplifyapp.com             no scheme            -> REJECT
```

The critical property holds: the parameter default `http://localhost:8080` satisfies its own `AllowedPattern`, so a default-parameter `cdk synth`/`deploy` does not fail CloudFormation validation. Had the pattern excluded `localhost:8080`, every default deploy would break.

The jest check uses `new RegExp(pattern).test(...)`; CloudFormation anchors `AllowedPattern` to the full string while JS `test()` is substring-based, but the pattern is already anchored with `^` and `$`, so the test mirrors CloudFormation for the URL inputs in play.

### Test is load-bearing

The test resolves the parameter from the synthesized template (`findParameters('adminAppBaseUrl')`), pulls `AllowedPattern`, and asserts accept/reject across the default origin, the real Amplify origin, their trailing-slash variants, and a scheme-less host. Deleting the `allowedPattern` makes `AllowedPattern` undefined and the `new RegExp(pattern)` construction throws; weakening it to drop the trailing-slash constraint flips the two reject-on-slash assertions. Not tested: the doubled-slash concatenation itself against a non-localhost `adminAppBaseUrl` (still a synth-time token, not literal-matchable) and the frontend `redirect_uri` construction, so the two sides of the byte-for-byte contract remain paired by inspection, unchanged from v1.

### No unrelated drift

This commit touches only the `adminAppBaseUrl` parameter definition (allowedPattern, constraintDescription, expanded description, and a source comment on why the token cannot be normalized in JS), the README deploy note, and the new test. The callback/logout URL strings, the frontend redirect helpers, `AdminPage`/`BattlePage` wiring, the JWT authorizer, the WebSocket API, and scoring are identical to the v1 state. No em dashes were introduced in the changed lines (the em dashes present in README and lambda files sit in unchanged context outside this diff's hunks).
